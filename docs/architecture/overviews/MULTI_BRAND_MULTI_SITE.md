## 2. Architecture Layers

### 2.1 LMS Multi-Site (Open edX `django.contrib.sites`)

The LMS resolves the current site from the HTTP `Host` header using:

```
Host header → django.contrib.sites.Site → SiteConfiguration.site_values
```

`SiteConfiguration.site_values` is a JSON blob that overrides LMS settings per-request:
`PLATFORM_NAME`, `LMS_ROOT_URL`, `CMS_ROOT_URL`, `MFE_BASE_URL`, `THEME_NAME`,
`course_org_filter`, `logo_image`, `favicon_path`, and any arbitrary keys consumed by MFEs
via the `mfe_config` API.

The sites are declared in `multisite-sites.yml` and must be loaded into the LMS database
(via management command or Django admin). The YAML is the canonical source of truth for
what sites should exist; the database is the authoritative runtime state.

### 2.2 Token-Driven Theming

Design tokens flow through a single canonical source and are distributed to three consumers:

```
assets/branding/tokens.css (canonical, from Figma)
        │
        ├──→ infrastructure/tutor/themes/mereka/common/static/css/mereka-design-tokens.css
        │    (generated by scripts/branding/generate-tokens-from-canonical.sh)
        │
        ├──→ infrastructure/tutor/themes/mereka/scss/_tokens.scss
        │    (SCSS variables + CSS custom properties for LMS/Studio/MFE SCSS builds)
        │
        └──→ infrastructure/tutor/themes/mereka/common/static/css/mereka-overrides.css
             (runtime CSS loaded via head-extra.html; no build step)
```

Token names follow the `--mereka-color-*` namespace. Paragon bridge tokens
(`--pgn-color-primary-base`, `--pgn-typography-font-family-sans-serif`, etc.) are derived from Mereka tokens
in `_tokens.scss` and `mereka-overrides.css`, so MFE components automatically pick up
the Mereka palette.

**Per-tenant token overrides are not yet implemented.** The infrastructure for adding a
`css/custom.css` file per tenant directory (`tenants/{slug}/css/`) exists, but there is no
mechanism to inject per-tenant CSS into the served page at runtime. This is a documented gap
(see section 5).

### 2.3 MFE SITE_VARIANTS (Build-Time Coupling — Gap)

`tutor_env/env/plugins/mfe/build/mfe/env.config.jsx` currently contains a
`SITE_VARIANTS` hostname map that was intended to select per-site branding variants in MFEs.
As documented in `docs/reference/architecture/MFE_RUNTIME_CONFIG.md` (Phase 3), this map is a
**build-time coupling to the domain list** and should be replaced by a single
`MEREKA_SITE_VARIANT` key served from the LMS `mfe_config` API.

Current state of `SITE_VARIANTS` in the generated `env.config.jsx`:
- The env.config.jsx contains footer component definitions, dark-mode toggle wiring, and
  plugin slot assignments per MFE APP_ID.
- There is no active `SITE_VARIANTS` map in the rendered file — the footers use
  `getConfig().INDIGO_FOOTER_NAV_LINKS` for nav links and `config.LMS_BASE_URL` for asset
  paths. The hostname-based variant selection intended by T125 has not been implemented yet.

### 2.4 Caddy Routing

`deploy/k8s/base/apps/caddy/Caddyfile` routes all sites to the same LMS/CMS/MFE backends.
Multi-site resolution is transparent at the Caddy layer — each vhost is listed in the
Caddyfile, and the `Host` header is forwarded to the LMS which performs site resolution.

Sites present in the Caddyfile:

| Component | Domains |
|-----------|---------|
| LMS | `academyv2.mereka.io`, `academyv2.mereka.dev`, `preview.*`, `skillourfuture.academy.mereka.io`, `academy.biji-biji.com` |
| Studio | `studio.academyv2.mereka.io`, `studio.academyv2.mereka.dev`, `studio.academy.biji-biji.com` |
| MFE | `apps.academyv2.mereka.io`, `apps.academyv2.mereka.dev`, `apps.academy.biji-biji.com` |

`skillourfuture` shares the main Studio and MFE domains — it has an LMS-level site entry
and org filter but no dedicated Studio/MFE subdomain.

### 2.5 Multi-Tenancy Django Plugin (`mereka_tenancy`)

Location: `infrastructure/tutor/plugins/multi-tenancy/`

This Django app extends the existing Open edX `EnterpriseCustomer` model to add tenant-aware
configuration. It provides:

| Component | Purpose |
|-----------|---------|
| `TenantConfig` model | Stores `branding_config`, `sso_config`, `feature_flags` per tenant |
| `TenantResolutionMiddleware` | Sets `request.tenant_uuid` and `request.tenant_slug` from hostname |
| `provision_tenant` management command | Idempotent creation of Site + SiteConfiguration + EnterpriseCustomer + TenantConfig + OAuth2 app + Waffle switches |

The middleware resolution chain is:
```
Host header → Site → SiteConfiguration.ENTERPRISE_CUSTOMER_UUID → TenantConfig
```

The app is installed via `apply-patches.sh` (`mereka_tenancy` in `INSTALLED_APPS`,
`TenantResolutionMiddleware` inserted after `CurrentSiteMiddleware`).

**Database migration `0001_initial` creates the `TenantConfig` table.** The migration
must be run before the LMS can resolve tenants via the middleware.

### 2.6 Per-Tenant Brand Pack Asset Structure

```
infrastructure/tutor/themes/mereka/tenants/
├── _template/               # Copy this to create a new tenant
│   ├── branding.json        # Brand pack configuration
│   ├── logos/               # Logo assets (.gitkeep placeholder)
│   ├── favicons/            # Favicon assets (.gitkeep placeholder)
│   └── css/                 # Optional per-tenant CSS overrides
└── {tenant-slug}/           # Actual tenant (none provisioned yet)
```

The `_template/README.md` describes required and optional assets, references the
`specs/brand-pack-schema.json` JSON Schema, and lists validation commands.

The brand-pack schema (`infrastructure/tutor/plugins/multi-tenancy/brand-config-schema.json`)
defines the structure of `TenantConfig.branding_config` stored in the database:
- `tenant_id`, `display_name` (required)
- `logos.primary/white/favicon/footer` (absolute HTTPS URLs)
- `palette.primary/secondary/accent/background/text` (6-digit hex)
- `typography.font_family/heading_font/font_source_url`
- `footer.variant/copyright_holder/whatsapp/legal_links/social_links`
- `legal_doc_urls.terms/privacy/cookies`
- `fallback_tenant_id` (defaults to `"mereka"`)

### 2.7 Tutor Plugin Config Defaults

`infrastructure/tutor/plugins/mereka_lms.py` registers multi-site domain lists as Tutor
config keys:

```python
MEREKA_LMS_EXTRA_HOSTS = [
    "admin.academyv2.mereka.io",
    "academy.biji-biji.com",
    "learner.academyv2.mereka.io",
    "skillourfuture.academy.mereka.io",
]
MEREKA_LMS_EXTRA_CSRF_ORIGINS = [...]   # HTTPS versions of the above
MEREKA_SESSION_COOKIE_DOMAIN = ".academyv2.mereka.io"
MEREKA_CSRF_COOKIE_DOMAIN = ".academyv2.mereka.io"
```

These are applied to the LMS production settings patch (`ALLOWED_HOSTS`,
`CSRF_TRUSTED_ORIGINS`, `SESSION_COOKIE_DOMAIN`, `CSRF_COOKIE_DOMAIN`).

**Important**: Cookie domain `.academyv2.mereka.io` does not cover `academy.biji-biji.com`.
This is a known coupling documented in `MFE_RUNTIME_CONFIG.md` Phase 1 — the cookie domains
should move to runtime `mfe_config` keys to allow per-site overrides.

## 3. What a New Tenant Needs

To spin up a new site with config-only changes, the following steps are required. All steps
marked (CONFIG ONLY) do not require an image rebuild.

### Step 1 — DNS (CONFIG ONLY)

Add a DNS CNAME or A record for the new domain pointing to the LMS load balancer IP.
For `*.mereka.io` subdomains: Cloudflare A record.
For third-party domains (e.g. `academy.partner.com`): DNS-only (gray cloud) + Let's Encrypt.

### Step 2 — Caddyfile (CONFIG ONLY)

Add the new domain to the Caddyfile LMS block:
```
http://academyv2.mereka.io, ..., http://new-tenant.mereka.io {
```
Apply via `kubectl apply` on the Caddy ConfigMap + pod restart.

### Step 3 — Tutor plugin config (CONFIG ONLY)

Add the domain to `MEREKA_LMS_EXTRA_HOSTS` and `MEREKA_LMS_EXTRA_CSRF_ORIGINS` in
`infrastructure/tutor/plugins/mereka_lms.py`.

Run `./scripts/infra/tutor-config-save.sh` and apply the patch, then rolling restart LMS.

### Step 4 — Provision the tenant (CONFIG ONLY)

```bash
./scripts/tenants/provision-tenant.sh \
  --slug new-tenant \
  --name "New Tenant Name" \
  --domain new-tenant.mereka.io \
  --contact-email admin@new-tenant.example.com
```

This creates:
- Django `Site` + `SiteConfiguration` (with `PLATFORM_NAME`, `LMS_ROOT_URL`, etc.)
- `EnterpriseCustomer` + `TenantConfig`
- OAuth2 Application (`tenant-{slug}`)
- Waffle switches for feature flags

### Step 5 — Brand assets (CONFIG ONLY)

```bash
cp -r infrastructure/tutor/themes/mereka/tenants/_template \
      infrastructure/tutor/themes/mereka/tenants/new-tenant

# Add logo and favicon files
# Edit branding.json with tenant-specific values
```

Run `kubectl exec ... -- python manage.py lms collectstatic` to deploy assets without
a rebuild.

Validate the brand pack:
```bash
./scripts/tenants/validate-tenant-brand-pack.sh --slug new-tenant
```

### Step 6 — Update multisite-sites.yml (CONFIG ONLY)

Add the new site entry to `infrastructure/tutor/multisite-sites.yml`. This YAML is the
declarative source of truth for site configuration and should be kept in sync with the
database state.

### Step 7 — Verify

```bash
./scripts/qa/verify-multisite-config.sh prod
./scripts/qa/verify-multi-brand-site.sh
```

## 4. MFE Per-Tenant Configuration

MFE branding is driven by the `mfe_config` API endpoint (`/api/mfe_config/v1`). The LMS
resolves the site from the `Host` header (which Caddy forwards) and returns the
`SiteConfiguration.site_values` blob as part of the MFE config response.

To deliver per-tenant MFE branding **today** (without image rebuild):

1. Add the desired key to `SiteConfiguration.site_values` for the tenant's site:
   ```json
   {
     "MEREKA_SITE_VARIANT": "bijibiji",
     "MEREKA_FOOTER_CONFIG": { "copyright_holder": "Biji-Biji Initiative" }
   }
   ```
2. The MFE footer component reads `getConfig().INDIGO_FOOTER_NAV_LINKS` from the mfe_config
   response — add `INDIGO_FOOTER_NAV_LINKS` to `site_values` to override footer links
   per-site without a rebuild.

**MFE cookie domain limitation**: `SESSION_COOKIE_DOMAIN` and `CSRF_COOKIE_DOMAIN` are
currently hardcoded to `.academyv2.mereka.io` in the MFE Dockerfile. This means MFEs served
from `apps.academy.biji-biji.com` may have cookie domain mismatches. The fix (Phase 1 of
`MFE_RUNTIME_CONFIG.md`) removes these from the Dockerfile so the LMS serves them at
runtime via `mfe_config`.

## 5. Gap Analysis

The following items are infrastructure-ready (code exists) but not yet wired end-to-end:

| Gap | Status | What's needed |
|-----|--------|---------------|
| Per-tenant token CSS injection | Not implemented | Runtime CSS injection mechanism (e.g. `SiteConfiguration` CSS key → `<style>` tag in `head-extra.html`) |
| MFE SITE_VARIANTS → runtime key | Not implemented | Replace hostname map in `env.config.jsx` with `MEREKA_SITE_VARIANT` from `mfe_config` (Phase 3, `MFE_RUNTIME_CONFIG.md`) |
| MFE cookie domains per-site | Not implemented | Remove `SESSION_COOKIE_DOMAIN`/`CSRF_COOKIE_DOMAIN` from Dockerfile (Phase 1, `MFE_RUNTIME_CONFIG.md`) |
| `bijibiji` dedicated Studio subdomain | Partial | `studio.academy.biji-biji.com` is in Caddyfile but points to shared Studio |
| `skillourfuture` dedicated MFE subdomain | Not present | Shares `apps.academyv2.mereka.io`; `mfe_config` host resolution works but no dedicated URL |
| Per-tenant logo assets on disk | Not present | `tenants/` dir has `_template` only; actual tenant asset directories are empty |
| `multisite-sites.yml` logo_image overrides | Partial | All three sites still reference the default Mereka logo URL |
| Tenant branding_config DB population | Not done | `TenantConfig.branding_config` is not populated for any live tenant |
| `mereka_tenancy` migration in live cluster | Unverified | `0001_initial` migration must have run before middleware is active |

The following items are working end-to-end:

| Capability | Evidence |
|------------|---------|
| Three-site LMS routing via `Host` header | Caddy Caddyfile + `SiteConfiguration` in `multisite-sites.yml` |
| Per-site `course_org_filter` | Each site in `multisite-sites.yml` has distinct org filter |
| `THEME_NAME: mereka` on all sites | Verified by `verify-multisite-config.sh` |
| `TenantResolutionMiddleware` code | `infrastructure/tutor/plugins/multi-tenancy/middleware.py` |
| `provision_tenant` management command | `infrastructure/tutor/plugins/multi-tenancy/management/commands/provision_tenant.py` |
| Brand-pack template + validation script | `tenants/_template/` + `validate-tenant-brand-pack.sh` |
| Tutor plugin: domain lists in ALLOWED_HOSTS | `mereka_lms.py` config defaults |
| Design token pipeline (canonical → generated) | `assets/branding/tokens.css` → `mereka-design-tokens.css`, `_tokens.scss`, `mereka-overrides.css` |

## 6. Configuration Reference

### Required `SiteConfiguration.site_values` keys per site

| Key | Example | Purpose |
|-----|---------|---------|
| `domain` | `academy.biji-biji.com` | Self-reference for middleware validation |
| `site_name` | `Biji-Biji Academy` | Displayed in email subjects |
| `platform_name` | `Biji-Biji Academy` | Displayed in LMS UI |
| `LMS_ROOT_URL` | `https://academy.biji-biji.com` | Absolute URL for internal links |
| `CMS_ROOT_URL` | `https://studio.academy.biji-biji.com` | Studio link in LMS |
| `MFE_BASE_URL` | `https://apps.academy.biji-biji.com` | MFE base for discussion links |
| `THEME_NAME` | `mereka` | Comprehensive theming selector |
| `ENABLE_COMPREHENSIVE_THEMING` | `true` | Must be true |
| `course_org_filter` | `["BIJIBIJI"]` | Restricts course catalog to org |
| `logo_image` | URL to logo PNG | Header logo src |
| `favicon_path` | `mereka/images/favicon.ico` | Browser tab favicon |
| `ENTERPRISE_CUSTOMER_UUID` | UUID | Set by `provision_tenant` — enables tenant middleware |

### Tutor config keys (in `tutor_env/config.yml`)

| Key | Default | Purpose |
|-----|---------|---------|
| `MEREKA_LMS_EXTRA_HOSTS` | list of domains | Added to `ALLOWED_HOSTS` |
| `MEREKA_LMS_EXTRA_CSRF_ORIGINS` | list of HTTPS origins | Added to `CSRF_TRUSTED_ORIGINS` |
| `MEREKA_SESSION_COOKIE_DOMAIN` | `.academyv2.mereka.io` | LMS session cookie scope |
| `MEREKA_CSRF_COOKIE_DOMAIN` | `.academyv2.mereka.io` | LMS CSRF cookie scope |
