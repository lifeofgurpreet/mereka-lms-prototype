# m0u5.10.1 — `ENABLE_COURSEWARE_MICROFRONTEND` was a no-op flag; retraction

## What happened

PR #1875 (merged `e22ce708f` on 2026-04-19) added to
`deploy/k8s/base/apps/openedx/settings/lms/production.py`:

```python
FEATURES["ENABLE_COURSEWARE_MICROFRONTEND"] = True
```

The claim in #1875: this flag gates LMS routing of
`/courses/<id>/courseware` and `/courses/<id>/progress` to the Learning
MFE. Enabling it would close D-03 / D-04 / D-05 (courseware blockers).

**This claim is false in Tutor 21 (Ulmo).**

## Live evidence (post-rollout runtime verification)

After the full promotion chain completed (build `24628623317` →
bbi-infrastructure `#3341` merge at 12:35Z → ArgoCD sync → LMS pod
rolled to image `e7bfe2e0a9...`):

```bash
kubectl --context rke2-nonprod -n mereka-lms-dev exec deploy/lms \
  -- python manage.py lms shell -c \
  "from django.conf import settings; print('ENABLE_COURSEWARE_MICROFRONTEND =', \
   settings.FEATURES.get('ENABLE_COURSEWARE_MICROFRONTEND', 'NOT_SET'))"

# → ENABLE_COURSEWARE_MICROFRONTEND = NOT_SET
```

The flag did not apply, because the assignment in `production.py` lives
inside a settings file path that doesn't mutate `FEATURES` via the
`tutor` config pipeline. That's a separate defect worth filing.

More fundamentally:

```bash
kubectl exec deploy/lms -- grep -rln "ENABLE_COURSEWARE_MICROFRONTEND" /openedx/
# → only test files match (test_models.py, test_views.py, test_receivers.py)
```

Outside of test fixtures, the edx-platform Ulmo LMS **does not read
this flag anywhere**. It is not a gating mechanism for courseware MFE
routing in this platform version.

## What does gate courseware MFE routing in Ulmo

Based on upstream edx-platform source inspection:

- `LEARNING_MICROFRONTEND_URL` setting (already set in production.py,
  confirmed live: `https://apps.academyv2.mereka.dev/learning`)
- **Waffle flags** in `lms.djangoapps.courseware.toggles` — e.g.
  `COURSEWARE_MICROFRONTEND_PROGRESS_MILESTONES`, plus
  `CourseMicroFrontendFlag`. These are database-backed
  (`waffle_flag`) rather than settings-file flags.
- View-level checks in
  `lms/djangoapps/courseware/views/index.py` that use
  `is_mfe_enabled()` or similar helpers against the waffle flags.

The actual fix is to set the waffle flags via Django admin or a
management command, not by adding a `FEATURES[]` entry.

## Retraction

This PR removes the `FEATURES["ENABLE_COURSEWARE_MICROFRONTEND"] = True`
line from `production.py` and replaces it with a retraction comment
citing this evidence bundle. Per doctrine Rule 2 (retractions patch
source, not margins), the retraction lives at the source location
alongside a pointer.

The companion change in #1875 that added
`MFE_CONFIG.setdefault("LEARNING_MICROFRONTEND_URL", ...)` is
preserved — exposing `LEARNING_MICROFRONTEND_URL` in the MFE config
API response is useful regardless, and it is not a no-op.

## Lesson captured

**Two agents independently converging on a fix is NOT sufficient
validation that the fix is correct.** Both #1875's author and the
D-06 agent landed on `ENABLE_COURSEWARE_MICROFRONTEND`. Both found
references to `COURSEWARE_MICROFRONTEND*` in test files and assumed
they named the gating flag. Neither confirmed the flag was actually
read by the courseware routing logic in the running platform.

Amendment to the "two agents converging on same fix is signal"
heuristic (slice 60 MemPalace): that signal is reliable only if each
agent independently verified the root-cause mechanism via runtime
probe, not just by grep pattern matching. Convergence on a plausible-
looking-but-wrong fix is a known failure mode.

## Three-signal verification pattern held

The three-signal invariant (slice 61 / 62) caught this defect. If I
had stopped at "PR merged + Argo Synced" the wrong flag would have
been called live. Verifying the pod image SHA THEN exec'ing into the
pod to read the actual setting value surfaced the no-op.
