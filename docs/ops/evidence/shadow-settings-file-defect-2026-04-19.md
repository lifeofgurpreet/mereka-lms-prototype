# App-repo LMS settings files are shadow artifacts — runtime loads a different path

## The defect

`deploy/k8s/base/apps/openedx/settings/lms/production.py` and
`deploy/k8s/base/apps/openedx/settings/lms/development.py` look like
the source of truth for LMS Django settings. Many verifiers
(`verify-tenant-foundation.sh`, `verify-enterprise-sso.sh`,
`verify-csp-report-pipeline.sh`, etc.) read these files to assert
platform configuration.

**But the running LMS pod does not load these files.** At runtime,
the LMS loads settings from
`/openedx/edx-platform/lms/envs/tutor/production.py`, which is
generated by Tutor from
`infrastructure/tutor/plugins/mereka_lms.py` (and friends).

## Live runtime proof

Probed a running dev LMS pod (image `e7bfe2e0a9...` after full
post-#1879 build pipeline):

```bash
# Probe 1: check the runtime settings path
kubectl --context rke2-nonprod -n mereka-lms-dev exec deploy/lms \
  -- ls /openedx/edx-platform/lms/envs/
# → common.py, devstack.py, production.py, test.py, docs/, tutor/...
# The `tutor/` subdir contains the actual runtime-loaded production.py.

# Probe 2: find LEARNING_MICROFRONTEND_URL at runtime
kubectl exec deploy/lms -- grep -n 'LEARNING_MICROFRONTEND_URL' \
  /openedx/edx-platform/lms/envs/tutor/production.py
# → 1318:LEARNING_MICROFRONTEND_URL = "https://apps.academyv2.mereka.dev/learning"

# Probe 3: confirm app-repo shadow is a DIFFERENT file
find /home/runner/work/mereka-lms/mereka-lms -name production.py -path '*settings/lms*'
# → deploy/k8s/base/apps/openedx/settings/lms/production.py (NOT runtime)
```

Additionally, `MFE_CONFIG.setdefault("LEARNING_MICROFRONTEND_URL", ...)`
in the shadow file — added by #1875, preserved by #1881 — does NOT
reach the live `MFE_CONFIG` dict:

```bash
kubectl exec deploy/lms -- python manage.py lms shell -c \
  "from django.conf import settings; print(sorted([k for k in settings.MFE_CONFIG.keys() if 'LEARN' in k.upper()]))"
# → ['LEARNER_HOME_MICROFRONTEND_URL', 'LEARNING_BASE_URL']
# Note absence of LEARNING_MICROFRONTEND_URL.
```

## Why verifiers pass against the shadow file

Scripts like `scripts/qa/verify-tenant-foundation.sh` grep the shadow
file for expected patterns. Those greps succeed because the shadow
has the text; runtime behavior is unrelated.

This creates a **false-positive gate**: the verifier says "pass" even
when the runtime does not have the asserted configuration.

## Impact

1. **PR #1875** (slice 60) added
   `FEATURES["ENABLE_COURSEWARE_MICROFRONTEND"] = True` to the shadow
   file expecting to gate courseware MFE routing. Zero runtime
   effect. Verifiers still passed. Only caught via 4th-signal check
   (kubectl exec inside running pod). Retracted in #1881.

2. **PR #1875 also added** `MFE_CONFIG.setdefault(...)` for the same
   reason — same no-op. Retraction still pending (harmless noise in
   the shadow file; ideal cleanup is a follow-up PR that removes the
   line alongside this evidence bundle, not urgent).

3. **Historical concern**: any prior PR that edited
   `deploy/k8s/base/apps/openedx/settings/lms/{production,development}.py`
   expecting runtime effect produced a no-op. Scope unknown; audit
   candidate.

## The correct path

To change LMS runtime configuration:

- **Option A (Tutor plugin)**: edit
  `infrastructure/tutor/plugins/mereka_lms.py` or
  `infrastructure/tutor/plugins/_mereka_lms/` to add hooks that Tutor
  renders into the real settings file at image build.
- **Option B (patches)**: edit files under
  `infrastructure/tutor/patches/` that the `apply-patches.sh` script
  applies to the rendered Tutor output.
- **Option C (waffle flags)**: for feature-gated behavior that is
  normally controlled by waffle flags, use
  `kubectl exec deploy/lms -- manage.py lms waffle_flag <name> --activate`
  plus a seed migration so new environments inherit the state.

Not Option D (which I did in #1875): edit the shadow file and hope
it lands at runtime.

## Invariant captured

**"Verifier passes" is NOT runtime proof.** A verifier that reads a
shadow file passes against the shadow, not against runtime. For any
setting that gates runtime behavior, the verification must exec into
the pod and read `settings.<FOO>` or equivalent.

This is a specialization of the 4-signal verification invariant
captured in slice 63: the 4th signal (runtime exec) catches this
exact category of defect that signals 1–3 cannot.

## What the m0u5.10.1 investigation needs to continue

The API + MFE config + routing probes in this slice show **the LMS
side is correct**:

```bash
# course_home API: 200 OK, redirects to Learning MFE correctly
kubectl exec deploy/lms -- curl -s -H 'Host: academyv2.mereka.dev' \
  'http://localhost:8000/api/course_home/v1/course_metadata/course-v1:MEREKA+MCT1-EN+course' \
  | python3 -m json.tool | grep -iE 'course_home_url|tabs' | head -3
# → "url": "https://apps.academyv2.mereka.dev/learning/course/course-v1:MEREKA+MCT1-EN+course/home"
```

So D-03/D-04/D-05 are NOT LMS-routing defects. They're downstream:
MFE-side JavaScript error, CSP blocking, auth cookie not flowing
cross-subdomain, or upstream `frontend-app-learning` bug. A
browser-capable agent is required to diagnose further.
