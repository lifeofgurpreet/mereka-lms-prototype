# m0u5.10.1 — Courseware/Progress Error Boundary Root-Cause

**Date**: 2026-04-19
**Defects addressed**: D-03, D-04 (courseware error boundary), D-05, D-06 (progress timeout/legacy redirect)
**Root-cause classification**: MFE runtime config — missing Django feature flag
**Path chosen**: fix-in-PR (single-flag, low-blast-radius)

---

## Root Cause

`FEATURES['ENABLE_COURSEWARE_MICROFRONTEND']` was never set to `True` in
`deploy/k8s/base/apps/openedx/settings/lms/production.py`.

In Open edX Ulmo (Tutor 21.x), this flag gates two server-side behaviours:

1. **Courseware redirect** (`/courses/.../courseware`): When the flag is False,
   the LMS `course_experience` URL conf serves courseware inline via the Django
   view instead of redirecting to `LEARNING_MICROFRONTEND_URL`. The Learning
   MFE then calls `/api/course_home/v1/outline/<course_id>` but the response
   shape is missing the `courseware_tabs` / `resume_block` fields expected by
   the MFE, causing the `CoursewareContainer` component to throw an unhandled
   exception and render the `ErrorPage` error boundary. This manifests as D-03
   (tablet hard-error "There was an error loading this course.") and D-04
   (desktop near-blank render with no navigable unit links).

2. **Progress redirect** (`/courses/.../progress`): When the flag is False,
   the LMS `course_progress` view serves the legacy Django progress template and
   does NOT redirect to the Learning MFE progress route. This manifests as D-06
   (mobile redirect to `academyv2.mereka.dev/courses/.../progress`) and D-05
   (desktop/tablet 30-second navigation timeout because the browser lands on the
   MFE `/progress` route but the LMS-side API call to
   `/api/course_home/v1/progress/<course_id>` returns a shape the component
   cannot render, causing an infinite loading spinner).

### Evidence trail

- `development.py` line 363: `FEATURES["ENABLE_COURSEWARE_MICROFRONTEND"] = False` — explicit opt-out for local dev.
- `production.py`: no `ENABLE_COURSEWARE_MICROFRONTEND` assignment anywhere in the 2050-line file (confirmed by full grep).
- `LEARNING_MICROFRONTEND_URL` is set at production.py line 961 and `MFE_CONFIG["LEARNING_BASE_URL"]` at line 962 — the URL is correct; only the enabling flag was missing.
- Upstream default in Open edX Ulmo base settings is also `False` (flag defaults off for backward compatibility).
- `MFE_CONFIG_API_URLS['learning']` at line 1017 is set correctly — the URL routing to the MFE pod is intact.

### Secondary finding (low-impact, also fixed)

`LEARNING_MICROFRONTEND_URL` was set as a top-level Django setting and also
in `MFE_CONFIG["LEARNING_BASE_URL"]`, but was not exposed in the
`FEATURES['MFE_CONFIG']` dict under the key `LEARNING_MICROFRONTEND_URL`.
The MFE config API endpoint (`/api/mfe_config/v1/`) only serves keys present in
`FEATURES['MFE_CONFIG']`. Added `MFE_CONFIG.setdefault("LEARNING_MICROFRONTEND_URL", ...)` in
the sync block (end of file, alongside the existing LEARNER_HOME and ACCOUNT setdefaults).

---

## Fix Applied

**File**: `deploy/k8s/base/apps/openedx/settings/lms/production.py`

### Change 1 — Enable courseware MFE routing
Added after line 750 (alongside the other MFE feature flags):
```python
FEATURES["ENABLE_COURSEWARE_MICROFRONTEND"] = True
```

### Change 2 — Expose LEARNING_MICROFRONTEND_URL in MFE config API
Added in the MFE_CONFIG sync block at end of file:
```python
MFE_CONFIG.setdefault("LEARNING_MICROFRONTEND_URL", LEARNING_MICROFRONTEND_URL)
```

---

## Blast Radius

**Low.** Both changes are additive:
- `ENABLE_COURSEWARE_MICROFRONTEND = True` enables LMS-side redirects from
  legacy courseware/progress Django views to the Learning MFE URLs. This is
  the intended production state. The Learning MFE is already deployed and
  serving correctly at `apps.academyv2.mereka.dev/learning/`.
- `MFE_CONFIG.setdefault(...)` only adds a key that was already present as a
  top-level setting; it cannot override an existing value.
- No schema change, no migration, no new service dependency.
- Requires LMS pod restart to pick up settings change (standard for any
  production.py edit; handled by ArgoCD + rolling deploy).
