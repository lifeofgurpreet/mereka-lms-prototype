# m0u5.1 Learning MFE — fix-sequencing plan

Companion planning doc for the 12 defects (D-01..D-12) captured in the
Learning MFE browser-proof bundle (#1870, refined by #1871 redaction).
This doc proposes root-cause hypotheses, fix surfaces, risk
classification, and sequencing. It deliberately does NOT prescribe
code changes — those ship as individual bug-fix PRs per defect.

**Reviewer provenance note**: architect investigation was done from a
branch that did not yet have the full #1870 evidence bundle on disk.
For D-01, D-02, D-04, D-05, D-07, D-08, D-10, D-11, D-12 the hypothesis
is classified `evidence-needed` — surface + component must be
reconciled against `docs/ops/evidence/m0u5.1-learning-mfe-browser-proof-2026-04-19.md`
before any bead is filed. D-03, D-06, D-09 are grounded in verbatim
text already surfaced in `CURRENT-OPERATOR-STATE.md`.

## Root-cause class summary

- **CSS / responsive**: D-02, D-05, D-09, D-11 — theme SCSS + brand tokens; fixable in this repo.
- **Routing / URL handling**: D-06 — MFE host routing + LMS redirect map.
- **API / data contract**: D-08 — `course_home` API shape.
- **Slot override mismatch**: D-01, D-04, D-07, D-10 — Insert vs Modify vs Hide+Insert semantics in `mereka_lms_mfe_slots.py`.
- **Upstream MFE bug**: D-03, D-09 (partial), D-12 — file upstream tickets at `openedx/frontend-app-learning`; carry mirror patches if upstream lag is unacceptable.

## Fix sequencing recommendation

1. **First** (highest impact, user-flagged, self-contained in own repo):
   - **D-09** — mobile 986px overflow. CSS-only tenant fix + viewport
     meta check. HIGH risk because the wrapper that overflows is likely
     upstream-controlled; tenant SCSS cap may need `!important` or a
     structural shadow-DOM override. Pair with upstream issue.
   - **D-06** — routing regression. Users silently served legacy
     Django view on mobile progress tab. Fix is overlay/redirect
     config, HIGH risk because it touches LMS side + Caddy. Requires
     careful rollback plan.

2. **Second (low-risk batch)**: D-02, D-05, D-11 — responsive SCSS
   tightening. One bead per defect, one PR each. Safe to parallelize.

3. **Wait (need more investigation)**: D-03, D-12 — confirm upstream
   lineage before patching. File `openedx/frontend-app-learning` issue
   with a reproduction first.

4. **Wait (slot semantics require m0u5.2 first)**: D-01, D-04, D-07,
   D-10 — require the m0u5.2 decision matrix (Insert vs Modify vs
   Hide+Insert) before touching `mereka_lms_mfe_slots.py`. Risk of
   hiding load-bearing API surface otherwise.

5. **API work**: D-08 — scope separately; may block or be blocked by
   a course_home contract freeze.

## Invariants captured

- **D-09 is not only a viewport-meta miss.** 986px at a 390px viewport
  implies a fixed-width child (likely content iframe wrapper or the
  outline tray in the open state). Viewport meta is a separate check
  worth adding to the verifier but is not sufficient alone.
- **Do not touch `_INSERT_SLOTS` Hint entries** to "fix" D-01, D-04,
  D-07, D-10 before m0u5.2 lands. Per the slot-retirement reframing
  in #1866 amendment: Hints are forward-compat API surface, not dead
  code.
- **Before filing beads**: pull
  `docs/ops/evidence/m0u5.1-learning-mfe-browser-proof-2026-04-19.md`
  from `main` and reconcile each `evidence-needed` row against the
  actual defect text + screenshots in the manifest.
