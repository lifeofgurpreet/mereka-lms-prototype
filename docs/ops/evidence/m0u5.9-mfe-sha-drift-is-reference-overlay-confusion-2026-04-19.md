# m0u5.9 — dev/prod MFE SHA drift is reference-overlay confusion

Bead `mereka-lms-m0u5.9` originally framed the observed dev/prod MFE
image SHA divergence (dev pin `c2719c3a`, prod pin `d6e9f14f`, live
dev pod running `9211c5479`) as a suspected **promotion bug OR
intentional staging lag**. Architect investigation finds the drift is
**neither** — it is an illusion created by looking at deprecated
reference-only overlays in this repo.

## Facts observed

### App-repo overlays carry explicit DEPRECATED banners

Both overlays state they are not consumed by ArgoCD:

- `deploy/k8s/overlays/rke2-nonprod/kustomization.yaml` — MFE pin
  `c2719c3a`. File header (lines 1–7): scheduled for **Wave 9 deletion**.
- `deploy/k8s/overlays/production/kustomization.yaml` — MFE pin
  `d6e9f14f623d26256ed55c0ef174a3fea19eada5`. Last synced 2026-03-24
  (line 47).

Both files carry explicit `DEPRECATED — boundary.debt — NOT consumed by
ArgoCD` banners and `MANAGED-BY: bbi-infrastructure — do not edit image
pins here`.

### The real ArgoCD source is `bbi-infrastructure`

Per `docs/reference/architecture/DEPLOYMENT_CONTRACT.md:29-33`, the
authoritative overlays are in `bbi-infrastructure`:

- `apps/mereka-lms/overlays/profiles/dev/kustomization.yaml:76` — MFE
  `9211c5479a9beebe38f13c051b4227a4f0f4a79c` (matches the running dev
  pod observed via `kubectl --context rke2-nonprod -n mereka-lms-dev
  get deploy mfe -o jsonpath='{.spec.template.spec.containers[0].image}'`).
- `apps/mereka-lms/overlays/staging/kustomization.yaml:13` — MFE
  `285057c16172be90684ea047e7c55d0b6678846a` (staging has its own pin,
  distinct from dev).
- `apps/mereka-lms/overlays/prod/kustomization.yaml:16` — MFE
  `d6e9f14f623d26256ed55c0ef174a3fea19eada5` (matches the app-repo
  reference — coincidence of the 2026-03-24 manual sync, not live
  signal).

The live running dev pod's image `9211c5479...` corresponds to app-repo
commit `9211c5479 defensive(release): guard relative_to in
generate_release_object help + RC-05 addendum (#1803)`. That's a recent
app-repo merge promoted to bbi-infra dev by the release chain — as
expected.

### Prod is parked (not stale)

`argocd/applications/mereka-lms-prod.yaml:64-69` in `bbi-infrastructure`:

- `syncPolicy.automated` is commented out
- Inline comment: "mereka-lms is deferred from RKE2 prod migration.
  Re-enable when LMS deployment begins."
- Production cluster is scaled to zero per the overlay headers

The bbi-infra prod pin `d6e9f14f...` is a **parked reference**, not a
live-serving image. Production mereka-lms traffic routes through
rke2-prod `mereka-lms` namespace (verified in slice 50 evidence
`docs/ops/evidence/gke-auth-workflow-classification-2026-04-19.md`);
that runtime is served from a different release chain and is currently
live, but bbi-infra's mereka-lms-prod ArgoCD Application itself is
intentionally parked.

### Enterprise portal tags

Both environments use `nreum-clean-202602200416` for
enterprise-admin-portal and enterprise-learner-portal. The fixed tag
looks like a mutable-tag risk, but:

- bbi-infra prod overlay digest-pins these entries
- app-repo prod overlay also carries digests (`853ce5…`, `185bbc…`)
- bbi-infra dev overlay uses **date-stamped** tags
  (`ab3112cb…-20260414044901`, `ea8651ec…-20260403232836`) with digest
  pins

The fixed tag is acceptable because it's digest-pinned in every
consumed location.

## Classification

**C. Wrong overlay authority.**

The bead's framing — "is this intentional staging lag or a promotion
bug?" — presupposes that both overlays are consumed and therefore the
SHA difference means something at runtime. That presupposition is
false. Neither app-repo overlay is consumed by ArgoCD. The observed
"drift" is between two reference-only pins that have no runtime effect.

Rejected alternative classifications:

- **(A) Intentional staging lag** — no, because the app-repo prod pin
  is not consumed. A lag between dev and prod *would* be relevant, but
  only between consumed bbi-infra overlays, where the current state is
  deliberate parking of prod, not lag.
- **(B) Stale prod** — no, for the same reason.

## Remediation

1. **Close `mereka-lms-m0u5.9` as "no real drift — reference overlay
   confusion."** Cite `DEPLOYMENT_CONTRACT.md:29-33` + the DEPRECATED
   banners on both overlays. No runtime action required.

2. **Accelerate Wave 9 deletion** of app-repo's
   `deploy/k8s/overlays/rke2-nonprod/` and
   `deploy/k8s/overlays/production/` directories. Both are already
   flagged for Wave 9; removing them permanently kills this class of
   bead (operators will no longer see misleading pins in the app repo).
   This is a standalone bead — open as
   `mereka-lms-m0u5.9.1` or under the Wave 9 parent if one exists.

3. **No change needed for enterprise portal tags.** Fixed tag is
   digest-pinned in bbi-infra prod; the app-repo reference for
   enterprise portals can be removed with Wave 9.
