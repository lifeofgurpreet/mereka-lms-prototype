# Shadow settings file defect — CORRECTION addendum

The previous evidence bundle
(`docs/ops/evidence/shadow-settings-file-defect-2026-04-19.md`, merged in
#1882) correctly established that `deploy/k8s/base/apps/openedx/settings/lms/*.py`
is a SHADOW and does not influence runtime. That finding holds.

**This addendum corrects the "correct path" guidance.** The original bundle
said the runtime settings file
(`/openedx/edx-platform/lms/envs/tutor/production.py`) is generated by Tutor
from `infrastructure/tutor/plugins/mereka_lms.py`. That is PARTIALLY WRONG.

## Runtime finding (2026-04-19T13:52Z)

The runtime LMS pod (dev, image `e7bfe2e0a9...`) mounts the settings file
from a **K8s configmap**, not from a Tutor-rendered filesystem path in the
image.

```bash
kubectl --context rke2-nonprod -n mereka-lms-dev get deploy lms -o json | python3 -c "
import json, sys
d = json.load(sys.stdin)
vols = [v for v in d['spec']['template']['spec']['volumes'] if 'configMap' in v]
mounts = d['spec']['template']['spec']['containers'][0]['volumeMounts']
for v in vols:
    print(f\"vol={v['name']} cm={v['configMap']['name']}\")
print('---')
for m in mounts:
    if 'settings' in m['name']:
        print(f\"vol={m['name']} path={m.get('mountPath')}\")
"
# → vol=settings-lms cm=openedx-settings-lms-patched-kd7mdd4cc6
# → vol=settings-lms path=/openedx/edx-platform/lms/envs/tutor/
```

The configmap `openedx-settings-lms-patched-kd7mdd4cc6` OVERWRITES the
Tutor-rendered settings directory inside the running pod. Any file in the
configmap wins over what Tutor built into the image.

## Implications

### The configmap is NOT rendered from the app-repo shadow files

Diffing the live configmap against the app-repo shadow file shows they are
completely different files — different headers, different byte counts (66059
vs the app-repo shadow file, which is 90k+). The live configmap contains a
sentinel `# P5.1 proof: settings-delivery-test sentinel (2026-03-16T02:13Z)`
dated 2026-03-16.

### The configmap is NOT rendered from the bbi-infra vendored copy either

`bbi-infrastructure/apps/mereka-lms/base/deploy/k8s/base/apps/openedx/settings/lms/production.py`
exists (86959 bytes) and is Argo-managed, but it is ALSO different from the
live configmap. The vendored copy was last touched in bbi-infra commit
`c3c304e2d4ac "fix(mereka-lms-dev): sync openedx probe contract (#2852)"` and
has diverged from the live configmap since.

### So what IS the live configmap rendered from?

**Unknown from this slice.** The configmap tracking annotation says
`argocd.argoproj.io/tracking-id: mereka-lms-dev:/ConfigMap:mereka-lms-dev/openedx-settings-lms-patched-kd7mdd4cc6`,
meaning Argo manages it. The source must be somewhere in the Argo
application's source tree (bbi-infrastructure/apps/mereka-lms/overlays/dev/
kustomize generator / patches / inline resources). Needs further
investigation.

## Revised "correct path" guidance

The previous bundle's "correct path" section listed:
- Option A (Tutor plugin): edit `infrastructure/tutor/plugins/mereka_lms.py`
- Option B (patches): edit `infrastructure/tutor/patches/*`
- Option C (waffle flags): `manage.py lms waffle_flag ...`

**Option A and B are wrong** for anything that needs to reach the runtime
settings configmap. Tutor-rendered settings in the OpenEdX image are
overwritten by the configmap mount at runtime. Options A/B only matter for
changes that:
- Go into OTHER image files (e.g. python packages installed in the image,
  theme assets copied into the image, entrypoint scripts)
- Change the RENDERED production.py in the image BUT the configmap mount
  doesn't override a path they touch

For LMS Django settings changes that must take effect at runtime:

- **Option A' (bbi-infra authoritative source)**: find the source of
  `openedx-settings-lms-patched-*` in the Argo-managed bbi-infra overlay
  (likely a kustomize configMapGenerator or inline resource) and edit that.
- **Option B' (DB-backed config)**: for feature-gated behavior normally
  controlled by waffle flags, use
  `kubectl exec deploy/lms -- manage.py lms waffle_flag <name> --activate`
  plus a seed migration.
- **Option C' (environment variable)**: if the setting can be read via
  `os.environ.get(...)`, add it to the LMS environment via Infisical →
  ExternalSecret → K8s env var.

## Impact on prior conclusions

1. **#1875's `FEATURES["ENABLE_COURSEWARE_MICROFRONTEND"] = True` retraction
   still holds** — the edit was in a shadow file that no runtime surface
   consumes. But the remediation path proposed ("add to Tutor plugin") was
   wrong. Correct remediation: edit the bbi-infra-managed configmap source,
   or use a waffle flag if the setting is backed by one.

2. **Warning headers added in #1883 still correct** — the app-repo shadow
   files really are not loaded at runtime. The header's pointer list
   ("Tutor plugin hook / Tutor patch / waffle flag") is PARTIALLY CORRECT:
   waffle flag still applies, but for Django settings the pointer should
   say "edit the bbi-infra-managed configmap source" instead of "edit the
   Tutor plugin".

3. **`mereka-lms-vfd5` (Tutor plugin LEARNING_MICROFRONTEND_URL exposure)**
   — needs re-scoping. The bead says "Correct path: Tutor plugin".
   Corrected: "Correct path: whichever source renders
   `openedx-settings-lms-patched-*` configmap". The Tutor plugin only
   matters if the configmap is DERIVED from the Tutor-rendered
   production.py (which it appears NOT to be, based on the sentinel date).

4. **Audit scope expands** — the shadow-settings audit bead
   (`mereka-lms-mefk`) must also trace:
   - What source renders `openedx-settings-lms-patched-*`?
   - Are there drift markers (sentinel dates) that show how stale the
     configmap is vs either shadow copy?
   - Which historical PRs added to the bbi-infra vendored copy but NOT to
     the configmap source (or vice versa)?

## Doctrine impact

The 4-signal verification invariant STILL holds — runtime exec exposed both
the app-repo shadow defect (slice 63-64) AND this configmap layer (slice 67).
The lesson refines: "runtime settings arrive through a chain of surfaces;
trace the chain to the actual source before claiming to have found the
authoritative file."
