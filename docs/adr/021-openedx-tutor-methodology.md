# ADR-021: Open edX / Tutor Deployment Methodology

**Status**: Accepted
**Date**: 2026-03-03
**Deciders**: Gurpreet Singh (Founder / Platform Owner)

<!-- Last verified: 2026-03-03 -->

## Context

As the Mereka Academy platform grows, more agents (human and AI) contribute to the Open edX deployment. Without a single document that captures the founding methodology, agents make local decisions that are individually reasonable but collectively inconsistent — e.g., patching Dockerfiles by hand when a supported hook exists, or running heavy image builds in CI on every push.

This ADR codifies the six decisions that form the Mereka LMS deployment methodology. These are operator-level decisions that define the boundaries within which all implementation work happens. They are not up for re-evaluation on a per-task basis. An agent that needs to deviate from any of these decisions must raise the question with the platform owner before proceeding.

## Decision

### 1. Release Line: Ulmo (Tutor 21.x)

We target the **Ulmo** Open edX release running on **Tutor 21.x**. This is the current community-supported release as of the date of this ADR.

Rules:
- No mixing of release tooling across release lines (e.g., no Tutor 18.x plugins in a Tutor 21.x environment).
- `tutor` from PyPI is the only supported install method. The `main`/`master` branch of the Tutor repository is **not for production** — it may generate templates that break patching assumptions without warning.
- Patch releases within 21.x (e.g., 21.0.1, 21.1.0) may be applied as needed. Major version upgrades (e.g., 21.x → 22.x) follow the process in ADR-019.
- The version pin is canonical at `.github/workflows/build-tutor-images.yml`. Any reference in documentation that disagrees with the workflow file is incorrect.

### 2. Customization Method: Tutor Plugin API

All Open edX customizations that can be expressed as Tutor hook callbacks **must** use the plugin API. Dockerfile surgery (editing Tutor-generated Dockerfiles by hand or via sed/Python string replacement) is the legacy approach and is being actively migrated out.

The supported plugin location is `infrastructure/tutor/plugins/mereka_lms.py`.

**Hooks to use (in order of preference)**:

| What to customize | Hook to use |
|---|---|
| Per-MFE npm packages | `mfe-dockerfile-post-npm-install` or `mfe-dockerfile-post-npm-install-<mfe>` |
| MFE build-time environment | `mfe-env-config-buildtime-imports`, `mfe-env-config-buildtime-definitions` |
| MFE runtime environment | `mfe-env-config-runtime-imports`, `mfe-env-config-runtime-definitions` |
| Frontend plugin slot overrides | `tutormfe.hooks.PLUGIN_SLOTS` |
| Platform image customization | `openedx-dockerfile-pre-assets`, `openedx-dockerfile-post-python-requirements` |
| LMS/CMS Django settings | `OPENEDX_LMS_PRODUCTION_SETTINGS`, `OPENEDX_CMS_PRODUCTION_SETTINGS` |
| Rendered env file patches | `ENV_PATCHES` |

**What is not a plugin hook**: file-copy operations (syncing theme assets, logo files, font directories) cannot be expressed as Tutor hooks and continue to live in `infrastructure/tutor/apply-patches.sh`. This script handles file-system work only — not configuration patches. See ADR-006.

**Current debt to eliminate**:
- `infrastructure/tutor/patches/mfe-node.sh` — 500+ lines of Dockerfile surgery
- `infrastructure/tutor/patches/brand-package.sh` — brand injection via sed/Python string replacement
- `infrastructure/tutor/patches/footer-component.sh` — footer component injection via string replacement

These must migrate to supported hooks in `mereka_lms.py`. Do not add new Dockerfile surgery. If the needed hook does not exist, open an issue upstream or implement the change differently.

### 3. Frontend Strategy: Plugin Slots + Design Tokens + @edx/brand

MFE customization follows OEP-48 and OEP-65:

- **Component overrides** (headers, footers, custom UI): Use `tutormfe.hooks.PLUGIN_SLOTS` to register Frontend Plugin Framework (FPF) slot overrides. Direct plugins are preferred over iFrame plugins for lightweight components that need MFE React context.
- **Visual styling** (colors, fonts, spacing): Use the `@edx/brand` package pattern (design tokens + Paragon CSS variables). Not inline SCSS injection into MFE source trees.
- **Indigo theming** does not style MFEs directly. Indigo is a Tutor plugin for the LMS/CMS Django template layer. MFE styling goes through `@edx/brand` and the Paragon design token system.
- Do **not** copy or modify `env.config.jsx` directly at the Dockerfile level. `env.config.jsx` is generated by Tutor at render time; write the plugin hook that produces the correct content.

The current implementation in `mereka_lms.py` uses `PLUGIN_SLOTS` for MerekaFooter and MerekaHeaderLogo. That pattern is the reference. See ADR-014 for the phased migration plan.

### 4. edx-platform Fork Base: Latest Release Tag

When we maintain a fork of `edx-platform` (for custom XBlocks, Django app overrides, or settings), the fork base must be the **latest tag on the named release** (e.g., `open-release/ulmo.1`).

Do **not** base the fork on:
- `master` — moves constantly, Tutor warns it is "overwhelmingly likely to fail"
- `release/ulmo` (or equivalent branch) — may be ahead of what Tutor expects, causing template/patch breakage

After each Tutor upgrade, re-evaluate the fork base tag and rebase if needed. The fork diff must stay minimal — only patches that cannot be contributed upstream or applied via Tutor hooks.

### 5. CI Methodology: Validation, Not Discovery

CI is a validation gate. It does not substitute for local proof-of-work.

**Anti-patterns we eliminated (2026-03-03)**:
- Using CI as the primary debugger (45-min blind failure loops)
- Runtime DinD MTU hacks (nsenter, SIGHUP, SIGTERM) that never worked
- No real BuildKit cache strategy — every build was a cold start
- Dead code for GitHub-hosted runners we stopped using
- Mixing infrastructure debugging (ARC routing, MTU) with product debugging (theme, auth)

**Rules**:
- **Local preflight first**: Before pushing a branch, run `scripts/ci/preflight-check.sh`. This renders the Tutor environment with CI-matching versions, validates generated Dockerfiles, and completes in under 60 seconds. Only push when the local run is clean.
- **CI validates on branch/PR**: CI confirms that what worked locally also works in a clean environment.
- **One hypothesis per PR**: PRs should represent a single, understood change. Do not push speculative changes to CI hoping it reveals what is wrong. Debug locally, then push the fix.
- **Never debug on main**: `main` must always be green. Experimental builds belong on feature branches.
- **Heavy builds on ARC runners only**: The `mereka-k8s-heavy-builders` runner pool (4CPU/12GB + Docker-in-Docker) is the only permitted target for image builds in CI. GitHub-hosted runners are not supported for builds.
- **Registry-backed BuildKit cache is mandatory**: The build pipeline uses `docker/build-push-action` with `cache-from: type=registry` and `cache-to: type=registry,mode=max`. This turns a 30-45 minute cold build into a ~5 minute incremental build on warm cache. The cache refs are `$REGISTRY/openedx:buildcache` and `$REGISTRY/mfe:buildcache`.
- **Platform problems are not workflow problems**: Infrastructure issues (MTU, DinD configuration, runner resource limits) are solved at the platform level (ARC RunnerScaleSet spec, ConfigMaps, Helm values), not by adding workaround steps to the workflow.

**Build pipeline architecture** (`build-tutor-images.yml`):
1. Tutor renders the exact Dockerfiles (`tutor config save` + `apply-patches.sh`)
2. DinD MTU is verified (fail in 2 seconds, not after 30 minutes)
3. `docker/build-push-action` with `docker-container` buildx driver builds directly from the rendered Dockerfile with registry cache
4. Image is pushed + loaded locally for branding verification, SBOM, and Trivy scan

**Local preflight minimum**:
```bash
# Must pass before pushing
scripts/ci/preflight-check.sh   # Renders + validates in <60s
make lint                        # Lint gate
```

### 6. Separation of Concerns: Six Independent Tracks

These six concerns are independent. A decision in one track does not imply anything about another track. Agents must not conflate them:

| Track | What it covers | Where it lives |
|---|---|---|
| **Release line** | Which Open edX + Tutor version we run | `docs/adr/019`, version pins in CI workflows |
| **Customization mechanism** | How patches reach the running system | `docs/adr/006`, `infrastructure/tutor/plugins/` |
| **Frontend strategy** | How MFE visual customization is expressed | `docs/adr/014`, `mereka_lms.py` PLUGIN_SLOTS |
| **Build validation** | Fast local proof-of-work before CI | Local preflight scripts, <5 min |
| **Heavy builds** | Full image builds for production | ARC heavy runners only, with Docker layer cache |
| **Change control** | How changes get to production | Branch → local proof → PR → merge → ArgoCD |

Example of conflating tracks (wrong): "We're staying on Tutor 18.x (release line), so I'll use the old Dockerfile surgery approach (customization mechanism)." The customization mechanism decision is independent of the release line decision. Plugin API is the correct mechanism on all supported release lines.

## Consequences

### Positive

- Agents (human or AI) have a single document to consult before starting any Open edX customization work.
- The plugin API survives Tutor upgrades. Dockerfile surgery does not. Migrating legacy patches reduces the per-upgrade audit burden.
- Plugin slot + design token approach enables frontend customizations without forking MFE repositories.
- Local preflight + CI separation means CI provides a meaningful signal rather than being a slow feedback loop.
- Separating the six tracks prevents category errors (e.g., treating a release line change as requiring a CI methodology change).

### Negative

- Tutor plugin API requires understanding Tutor's hook system, which is less immediately obvious than editing a Dockerfile.
- The `PLUGIN_SLOTS` hook (`tutormfe.hooks.PLUGIN_SLOTS`) was introduced in Tutor 21. Any environment running an earlier Tutor version will need the fallback pattern shown in `mereka_lms.py`.
- Legacy debt (three patch scripts) must be migrated before the next major Tutor upgrade. Until then, `apply-patches.sh` must be audited on every upgrade.

### Risks

- **Tutor hook API changes**: If Tutor changes hook names between 21.x and 22.x, the plugin will need updates. Mitigation: ADR-006 Layer 2 (git hook) and Layer 3 (CI verification) will catch hook API drift before it reaches production.
- **Design token adoption gap**: MFE styling is partially on the old SCSS overlay path. Until the phased migration (ADR-014) completes, there is dual-mode complexity. Do not introduce new SCSS overlay patches; route all new styling through `@edx/brand` tokens.
- **ARC runner availability**: If ARC heavy runners are unavailable (e.g., after a cluster incident), image builds in CI will be blocked. Mitigation: maintain the ability to run `tutor images build` locally and push images directly to Artifact Registry via `gcloud` auth.
