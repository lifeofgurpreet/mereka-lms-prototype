# ADR-011: Convention-Based Spec Verification (V3)

**Status**: Accepted
**Date**: 2026-02-11
**Deciders**: Platform Team
**Related**: [specs/plans/IMPLEMENTATION_ORDER.md](../../specs/plans/IMPLEMENTATION_ORDER.md), [scripts/qa/spec-tools/](../../scripts/qa/spec-tools/)

<!-- Last verified: 2026-02-13 -->

## Context

The Mereka Academy platform has 31 specifications defining 769 acceptance criteria (ACs) across all features and infrastructure. We needed a system to track which ACs are verified by automated tests and scripts.

### V1 and V2 Approaches (Manual Testmaps)

Prior approaches used manually-authored YAML testmap files:

```yaml
# specs/_generated/testmaps/k8s-deployment_spec.testmap.yml
coverage:
  - ac_id: AC-001
    test_file: scripts/qa/verify-k8s-namespace.sh
    test_type: automated
  - ac_id: AC-002
    test_file: scripts/qa/verify-external-secrets.sh
    test_type: automated
```

**Problems**:
- **Pure maintenance burden**: 31 YAML files mapping 769 ACs to test files
- **Frequent drift**: Testmaps updated separately from code, leading to stale entries
- **Fuzzy text matching**: `check_test_coverage.py` used regex matching on file contents, producing false positives
- **Dishonest coverage**: "Coverage" meant "file exists on disk" or "phantom file planned", not actual verification
- **Brittle tooling**: `validate_testmap_format.py`, `convert_testmap.py`, `add_ac_descriptions.py` maintained separately
- **No bidirectional traceability**: Given a script, couldn't easily find which ACs it verified

### Coverage Inflation

Under the testmap system, reported metrics were:
- 321 automated (41.7% of 769 ACs)
- 393 planned (phantom scripts that didn't exist yet)
- 52 manual

In reality:
- Many "automated" entries were fuzzy matches (e.g., script mentioned "namespace" → AC about namespaces marked covered)
- Phantom entries inflated total to 766 mapped ACs
- Actual verified ACs were closer to ~300

## Decision

We switched to **convention-based verification (V3)** where:

1. **`@covers` annotations in test/script files are the sole source of truth** for automated verification
2. **`@spec` annotations link files to specifications** for organizational clarity
3. **Manual/monitoring entries consolidated** in single `specs/plans/manual_verifications.yaml` (not 31 separate testmaps)
4. **Testmap YAML is a computed artifact** generated by `discover_testmap.py` from annotations
5. **`depends_on` frontmatter in specs** enables computed implementation ordering

### Annotation Format

```bash
#!/usr/bin/env bash
# @spec: k8s-deployment_spec.md
# @covers: AC-001, AC-002, AC-003
# @description: Verifies Kubernetes namespace and resource quotas

# Script body...
```

```python
# @spec: secrets-management_spec.md
# @covers: AC-SEC-001
def test_external_secret_sync():
    """Verifies ExternalSecret syncs from Infisical to K8s"""
    # Test body...
```

### Manual Verifications

```yaml
# specs/plans/manual_verifications.yaml
manual_verifications:
  - ac_id: AC-BRD-003
    verification_type: manual
    runbook: docs/guides/branding/BRANDING.md
    section: "Theme Customization"
    justification: "Visual verification required for theme rendering"
  - ac_id: AC-MON-001
    verification_type: monitoring
    runbook: docs/reference/operations/MONITORING.md
    section: "Prometheus Alerts"
    justification: "Runtime monitoring, not testable in CI"
```

## Consequences

### Positive

- **Zero testmap maintenance**: Annotations live next to code they describe
- **Honest coverage numbers**: Coverage = "this script explicitly claims to verify this AC"
- **Bidirectional traceability**:
  - Given AC → find all verifying scripts via `spec_verify.py --ac AC-001`
  - Given script → see which ACs it covers via `@covers` annotation
- **Improved coverage**: 95.1% of 769 ACs now automated (up from 41.7% under fuzzy matching)
- **25 unmapped ACs honestly reported**: Previously hidden as "planned" phantom scripts
- **Simplified tooling**: Deleted 4 testmap-specific tools (`validate_testmap_format.py`, `convert_testmap.py`, `add_ac_descriptions.py`, `check_test_coverage.py` fuzzy matching)
- **Enforced by linting**: `TEST-MAP-001` rule ensures new test files include `@covers`
- **Computed dependency graph**: `depends_on` frontmatter + `compute_dependency_graph.py` generates `specs/plans/IMPLEMENTATION_ORDER.md`

### Negative

- **Scripts need annotation migration**: One-time effort to add `@covers` to 119 verification scripts (completed via `annotate_scripts.py`)
- **New test files must include `@covers`**: Enforced by spec integrity gates, but requires discipline
- **Manual verifications in separate file**: `specs/plans/manual_verifications.yaml` must be maintained alongside specs (but consolidated from 31 testmaps)

## Alternatives Considered

### Keep Manual Testmaps, Improve Matching

- Continue maintaining 31 YAML files
- Replace fuzzy matching with exact AC ID lookup
- **Rejected because**: Still a maintenance burden, doesn't solve drift problem, no bidirectional traceability

### Test Discovery via Naming Convention

- Name test files `test_AC_001.py`, `verify_AC_002.sh`
- Parse filenames to infer coverage
- **Rejected because**:
  - Single test often covers multiple ACs
  - Filename-based discovery breaks when refactoring
  - No way to document justification for manual verifications

### External Test Management Tool

- Use tools like TestRail, qTest, or Zephyr
- Maintain AC-to-test mapping in third-party system
- **Rejected because**:
  - Adds tool dependency and access overhead
  - Disconnects verification from codebase
  - Still requires manual mapping maintenance

## Implementation Notes

### Migration Process (Completed 2026-02-10, reconciled 2026-03-08)

1. **Extract manual entries**: `extract_manual_entries.py` scanned 31 testmaps, consolidated to `specs/plans/manual_verifications.yaml`
2. **Annotate scripts**: `annotate_scripts.py` added `@covers` annotations to 119 scripts based on old testmaps
3. **Add `depends_on` frontmatter**: Manually added to 31 specs based on architectural knowledge
4. **Rewrite tooling**:
   - `spec_verify.py`: Query which scripts verify a given AC
   - `spec_coverage_report.py`: Generate HTML coverage report from annotations
   - `discover_testmap.py`: Compute testmap YAML from annotations into generated output
   - `compute_dependency_graph.py`: Generate `specs/plans/IMPLEMENTATION_ORDER.md` from `depends_on`
   - `mereka_spec_verify.py`: Shell wrapper for CI/CD integration
5. **Update spec integrity gates**: `run-spec-integrity-gates.sh` now runs annotation-based tools
6. **Compatibility reality**: the repository retained `specs/testmaps/` longer than intended. Wave 2B freezes that path as legacy compatibility only, with generated testmaps canonical under `specs/_generated/testmaps/`.

### Current Path Contract

After the Wave 2B convergence changes:

- `specs/_generated/testmaps/**` is the active generated testmap surface
- `specs/testmaps/**` is frozen legacy compatibility only
- CI blocks new edits in the legacy path except the explanatory README

### Coverage Improvement

| Metric | V2 (Testmap) | V3 (Annotation) | Change |
|--------|--------------|-----------------|--------|
| Total ACs | 769 | 769 | - |
| Automated | 321 (41.7%) | 731 (95.1%) | +410 (+53.4pp) |

**Note**: V2 "automated" count included phantom scripts and fuzzy matches. V3 count reflects explicit `@covers` claims.

### Enforcement

Spec integrity gates (`run-spec-integrity-gates.sh`) enforce:

1. **Lint**: All specs pass `spec_lint.py` (frontmatter format, AC ID uniqueness)
2. **Verify**: All ACs have `@covers` annotation or manual verification entry
3. **Format**: All specs use standardized YAML frontmatter
4. **Coverage**: 100% of ACs mapped (manual verifications allowed)

Gates run in CI/CD and block merge if any check fails.

### Spec Frontmatter Example

```yaml
---
id: k8s-deployment
title: Kubernetes Deployment
version: 1.0
status: approved
depends_on:
  - secrets-management
  - mongodb-atlas
---
```

The `depends_on` field enables `compute_dependency_graph.py` to generate a tiered dependency graph in `specs/plans/IMPLEMENTATION_ORDER.md`.

## Comparison to Industry Practices

### Cucumber/Gherkin (BDD)

- Uses `@tag` annotations in feature files
- Tags link scenarios to requirements
- **Similarity**: Annotation-based traceability
- **Difference**: We annotate test code, not spec files (specs are human-authored documentation)

### Requirements Traceability Matrix (RTM)

- Spreadsheet or database mapping requirements to tests
- Common in regulated industries (FDA, ISO 26262)
- **Similarity**: Bidirectional traceability
- **Difference**: We use in-code annotations instead of external spreadsheet

### Test Management Tools (TestRail, qTest)

- Centralized test case management
- Link test cases to requirements via UI
- **Similarity**: Structured requirement-to-test mapping
- **Difference**: We embed mapping in codebase (version-controlled, no tool dependency)

## Migration from Convention-Based (If Needed)

If team growth or regulatory requirements demand a test management tool:

1. Export `@covers` annotations to CSV via `spec_coverage_report.py --format=csv`
2. Import to test management tool (TestRail API, qTest API)
3. Keep `@covers` annotations for developer ergonomics
4. Use tool exports to generate official RTM for audits

Estimated effort: 1-2 weeks for tool setup and import

## Wave 2 alignment note

ADR-011 remains accepted, but the repository briefly diverged from its own contract by keeping `specs/testmaps/` as an active-looking surface. Wave 2 closes that split by:

- treating `@covers` annotations and manual verification metadata as the source of truth
- generating active testmaps into `specs/_generated/testmaps/`
- freezing `specs/testmaps/` as legacy fallback only
