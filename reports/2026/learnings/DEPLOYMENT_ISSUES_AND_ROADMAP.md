## 1. MFE Dockerfile — Version Mismatch (Redwood Apps + Ulmo Packages)

### What happened
The MFE Dockerfile (generated by `tutor config save` + `apply-patches.sh`) mixes two different Open edX release eras:

| Component | Era | Source |
|-----------|-----|--------|
| MFE app source (authn, discussions, etc.) | **Redwood** (`open-release/redwood.3`) | tutor-mfe plugin defaults |
| Brand package (`@edly-io/brand-openedx#indigo-2.5.0`) | **Ulmo** | apply-patches.sh injection |
| `@openedx/frontend-plugin-framework@^1.8.0` | **Ulmo** | apply-patches.sh injection |
| `@openedx/frontend-slot-footer` (transitive) | **Ulmo** | pulled in by plugin-framework |

This caused 4 cascading build failures:
1. `frontend-app-admin-console` had no `open-release/redwood.3` tag → build abort
2. Ulmo brand dark SCSS theme called `button-variant()` from redwood-era paragon → dart-sass mixin error
3. `frontend-slot-footer` (ulmo) needed `@edx/frontend-component-footer` which redwood apps don't install → webpack module not found
4. `frontend-app-discussions` webpack CLI prompt in non-interactive Docker → no dist produced, silent failure

### Workaround applied
Thin-layer image patch: pulled existing deployed image, `sed` CSS revision marker, pushed new tag. Fast but wrong — sourcemaps are stale, image provenance is misleading, underlying build is still broken.

### Proper fix needed
- Update `apply-patches.sh` to replace all `open-release/redwood.3` MFE source refs with `release/ulmo.1` (or latest ulmo tag per app)
- Verify each app has a `release/ulmo.*` tag — `frontend-app-authn` does (`release/ulmo.1`), check others
- Remove `--legacy-peer-deps` hacks once all apps are ulmo-era (deps will be compatible)
- Do a full clean rebuild and push as canonical MFE image

### Beads to create
- `fix-mfe-dockerfile-ulmo-migration` — update all app refs to ulmo, full rebuild

## 2. MFE Dockerfile Lives in `tutor_env/` — Gitignored

### What happened
`tutor_env/` is gitignored. The Dockerfile that drives the MFE image build has no git history, no diffs, no way to know what changed between builds. The Feb 10 build worked; the Feb 20 rebuild didn't. We couldn't compare.

### Proper fix needed
- Either: copy the Dockerfile into a tracked path (e.g. `infrastructure/tutor/mfe-build/Dockerfile`) after each `apply-patches.sh` run
- Or: make `apply-patches.sh` emit a build manifest (what refs, what versions) to a tracked file after patching
- Add a `make mfe-build-snapshot` target that copies the current Dockerfile to a dated artifact

## 3. No CI for MFE Image Builds

### What happened
MFE image builds are entirely manual. There's no pipeline that catches Dockerfile regressions. The version mismatch issues above would have been caught immediately if there were automated builds.

### Proper fix needed
- Add a CI job (GitHub Actions) that runs `tutor images build mfe` on PRs that touch `infrastructure/tutor/`
- Gate on: build succeeds + branding rev marker present in output CSS
- This is the single highest-leverage CI improvement available

## 4. Enterprise Admin Portal — Build-Time vs Runtime Env Vars (lyis)

### What happened
`frontend-app-admin-console` (ulmo) uses webpack `DefinePlugin` to substitute env vars at **build time**. The deployed image has unresolved `MISSING_ENV_VAR".<KEY>` placeholders in the compiled JS because no env vars were provided at build time.

We serve `env.config.js` as runtime config (`window.ENV_CONFIG`), but:
- The `index.html` doesn't include `<script src="/env.config.js">` — so the browser never loads it
- Even if it did, `window.ENV_CONFIG` can't patch already-compiled webpack placeholder strings in JS bundles

### Proper fix needed
**Option A (runtime injection — recommended):**
- The enterprise admin portal image uses a file server (Caddy/nginx) to serve static files
- Add an initContainer or entrypoint script that patches `index.html` on pod startup to inject `<script src="/env.config.js">` before serving
- The portal's JS must also use `window.ENV_CONFIG` fallback pattern (check if `frontend-app-admin-console` supports this)

**Option B (build-time bake-in — simpler):**
- Build the enterprise admin portal image with the correct env vars baked in via `--build-arg`
- Already doing this for `enterprise-mfe-env.js` as a ConfigMap — extend to build args

### Current state

## 5. Enterprise Admin Portal — Wrong Internal Service URLs

### What happened
`enterprise-mfe-env.js` originally had cluster-internal DNS names that browser JS can never reach:
- `http://enterprise-access:8000` (wrong port, cluster-internal)
- `http://enterprise-subsidy:8000` (wrong port, cluster-internal)
- `http://license-manager:8000` (wrong port, cluster-internal)

### Fix applied
Added Caddy path-prefix routes on `admin.academyv2.mereka.io` → internal services. Updated `enterprise-mfe-env.js` to use external HTTPS URLs. Committed `1c66529`.

### Lesson
When wiring MFE env configs for services: always check where the JS runs (browser), not where the pod runs. Internal cluster DNS is never reachable from browser.

## 6. ArgoCD Watches Main Branch, Not Feature Branches

### What happened
Fixes committed to `feat/23ry2-spec-dedupe-normalize` are not deployed until ArgoCD syncs. This creates a gap: "committed" ≠ "deployed." We had to manually verify deployed state was different from committed state when checking verification scripts.

### Proper fix needed
- Enforce PR → merge → deploy flow explicitly in the team workflow
- Or: set up a staging ArgoCD app that watches the feature branch for pre-merge validation
- Add a note in CLAUDE.md: "Committed on feature branch ≠ deployed. Always check ArgoCD sync status before running live verification scripts."

## Key Lessons

1. **Check where JS runs, not where the pod runs.** Cluster-internal DNS is never reachable from browser.
2. **Mixed-era dependencies cause cascading failures.** Ulmo packages on redwood app source = fragile. Upgrade all together.
3. **`tutor_env/` being gitignored is a blind spot.** Any file that drives a production build should be tracked or snapshotted.
4. **Thin-layer image patches are a last resort, not a pattern.** They work for string substitution but mislead on provenance and leave sourcemaps stale.
5. **No CI for MFE builds is the highest-risk gap.** Manual builds that take 30-60min with no automated validation will keep breaking.
6. **Check mail between build attempts.** Don't go 90min deep in a build loop without checking for coordinator updates.
