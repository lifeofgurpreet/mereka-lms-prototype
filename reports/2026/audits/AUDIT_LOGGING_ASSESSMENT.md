## 1. Purpose

This document captures the current state of audit and event logging across the Mereka LMS stack, identifies what Open edX provides natively, and outlines gaps. It is **not a compliance requirement**. Stakeholders have explicitly classified this as aspirational — lower priority than operational tasks.

Scope: LMS, CMS, Purchase Gateway, custom Django apps, and the observability stack.

## 2. What Open edX Provides Natively

### 2.1 Tracking Log (`tracking.log`)

Open edX emits structured JSON events to `tracking.log` for every significant learner interaction. This is the platform's built-in behavioural audit trail.

**Configuration** (`deploy/k8s/base/apps/openedx/settings/lms/production.py` lines 447–453):
```python
LOGGING["handlers"]["tracking"] = {
    "level": "DEBUG",
    "class": "logging.handlers.WatchedFileHandler",
    "filename": os.path.join(LOG_DIR, "tracking.log"),
    "formatter": "standard",
}
LOGGING["loggers"]["tracking"]["handlers"] = ["console", "local", "tracking"]
```

**What it captures**:
- Page views and navigation events
- Course enrollment and unenrollment
- Problem submissions and grades
- Video play, pause, seek events
- Certificate generation
- Forum post creation and edits
- Assessment attempts

**Current state**: Configured and active. Events write to container filesystem. Promtail ships container stdout/stderr to Loki (30-day retention). `tracking.log` file on disk is NOT separately shipped to Loki — it stays on the container filesystem and is lost on pod restart.

### 2.2 Django Admin Log (`django_admin_log`)

Django's built-in `django.contrib.admin` records every create, change, and delete action performed via the Django admin UI into the `django_admin_log` database table (MySQL). This provides an operator-level audit trail with no additional configuration.

**What it captures**:
- Which admin user performed the action
- The model and object ID affected
- The action type (addition, change, deletion)
- A human-readable change message (field-level diffs for changes)
- Timestamp

**Current state**: Active by default — Open edX has `django.contrib.admin` in `INSTALLED_APPS`. No explicit configuration needed.

### 2.3 User Retirement Audit (`user_api_userretirementstatus`)

The Open edX user retirement pipeline records each step of the account erasure process with timestamps and state transitions. This is a compliance-adjacent audit trail for GDPR/PDPA erasure requests.

**Retention**: 3 years post-completion (see `docs/policies/operations/DATA_RETENTION_POLICY.md`).

### 2.4 OEP-30 PII Annotations

Open edX models use `@pii_annotation` decorators to classify fields that contain personal data. This is metadata for the audit and export pipeline rather than a runtime audit log, but it enables automated data export and verification.

Reference: https://open-edx-proposals.readthedocs.io/en/latest/architectural-decisions/oep-0030-arch-pii-markup-and-auditing.html

## 3. Custom App Audit Surfaces

### 3.1 Purchase Gateway — `order_audit_log` Table (PostgreSQL)

**Location**: `services/purchase-gateway/app/models/order.py`

The Purchase Gateway has a purpose-built audit log table:

```python
class OrderAuditLog(Base):
    __tablename__ = "order_audit_log"
    id: Mapped[uuid.UUID]
    order_id: Mapped[uuid.UUID]      # FK to orders
    old_status: Mapped[str]           # Previous order status
    new_status: Mapped[str]           # New order status
    triggered_by: Mapped[str]         # Actor: "stripe_webhook", "admin", etc.
    timestamp: Mapped[datetime]       # UTC timestamp
    details: Mapped[dict | None]      # JSONB — arbitrary metadata
```

**What it captures**: Every order status transition, including which system/user triggered the change.

**Retention**: 7 years per Companies Act 2016 (Malaysia) — defined in `docs/policies/operations/DATA_RETENTION_POLICY.md`.

**Coverage**: Tests exist in `services/purchase-gateway/tests/unit/test_models.py` and `test_webhook_handler.py`.

### 3.2 Video Protection — `VideoAccessLog` Model (MySQL)

**Location**: `infrastructure/tutor/custom-apps/openedx_video_protection/models.py`

A per-access log for video playback attempts:

- Fields: `user`, `video_id`, `course_key`, `status` (ACCESS_GRANTED / ACCESS_DENIED), `denial_reason`, `timestamp`, `org_slug`
- Admin UI: read-only (`has_add_permission` and `has_delete_permission` return `False`)
- Cleanup: Celery task deletes records older than a configurable threshold (`tasks.py`)

**Current state**: Active in the custom app. Records are generated by the video protection middleware.

### 3.3 Django Admin Registrations in Custom Apps

Custom apps register their models with Django admin (read-only or limited write), providing an indirect admin-action audit trail via `django_admin_log`:

| Custom App | Admin-Registered Models |
|------------|------------------------|
| `openedx_video_analytics` | `VideoPlaybackEvent`, `VideoAnalyticsSummary` |
| `openedx_xqueue_graders` | `GraderSubmission`, `GraderQueueMetrics` |
| `openedx_push_notifications` | `DeviceRegistration` |
| `openedx_advanced_xblocks` | `RandomizedQuestionPool`, `AnswerShufflingState`, `DragDropInteraction`, `MathInputSubmission`, `XBlockGradebookEntry` |
| `openedx_mobile_api` | `MobileDevice`, `MobileBrandingConfig`, `MobileAppVersion`, `PKCEChallenge`, `MobileToken`, `APNsNotification` |
| `openedx_video_protection` | `SignedPlaybackToken`, `VideoAccessLog` |
| `openedx_mux_upload` | `MuxUpload` |

All admin-originated actions on these models are recorded in `django_admin_log`.

## 4. Observability Stack (Loki)

Application logs from all pods are shipped to Loki via Promtail:

- **Retention**: 30 days (`limits_config.retention_period: 720h`)
- **PII filtering**: Promtail `replace` stage masks email addresses and user IDs from LMS request logs before ingestion
- **Sentry**: Error telemetry for LMS, CMS, Discovery, Ecommerce, Credentials — see `docs/reference/operations/LOGGING_AND_SENTRY.md`

Loki is a log aggregation system. It is **not** a SIEM. It does not provide alerting on specific audit events, correlation across services, or tamper-evident storage.

## 5. Aspects Analytics (Not Yet Deployed)

Tutor-contrib-Aspects is the Open edX native analytics plugin. Its manifests exist in `deploy/k8s/base/plugins/aspects/` but are **not wired into the active kustomization graph** (tracked as task T148).

When deployed, Aspects provides:
- xAPI 1.0.3 events via the platform event bus → Ralph (xAPI LRS) → ClickHouse
- Rich learner event history (enrollment, grade, video, assessment events)
- Apache Superset dashboards for aggregate analytics

Aspects is a learner analytics pipeline, not a security audit log. It does not capture admin actions, API key usage, or system-level configuration changes.

## 6. Gap Analysis

| Audit Concern | Current State | Gap |
|---------------|--------------|-----|
| Learner behavioural events | tracking.log (active, 30-day Loki retention) | tracking.log on-disk not shipped to Loki; lost on pod restart |
| Admin actions (LMS/CMS Django admin) | `django_admin_log` in MySQL (active) | No export or alerting; queried only on demand |
| Order state transitions (Purchase Gateway) | `order_audit_log` table (active, 7-year retention) | No structured export tooling |
| Video access attempts | `VideoAccessLog` model (active) | Retention is configurable but not documented in central policy |
| Kubernetes API server audit | Not configured | GKE audit logs available via Cloud Logging but not imported into Loki/SIEM |
| Infisical/secrets access | Not captured in this repo | Infisical has its own audit log (platform-level) |
| Authentik admin actions | Not captured in this repo | Authentik has its own event log |
| Configuration changes (Tutor patches) | Git history (implicit audit) | No structured changelog per deployment |
| xAPI learning events (Aspects) | Manifests exist, not deployed | Aspects deployment tracked as T148 |
| SIEM integration | None | No forwarding to an external SIEM |
| Tamper-evident log storage | None | Loki and MySQL are mutable; no append-only guarantee |
| Centralized audit schema | None | Each subsystem uses its own schema |

## 7. What Open edX Does NOT Provide Natively

- **No unified audit log API** — there is no single endpoint or table that consolidates all audit events across the LMS.
- **No admin action alerting** — `django_admin_log` is queryable but does not trigger alerts on sensitive actions.
- **No API access log** — REST API calls to the LMS/CMS are logged at the HTTP level (Caddy/nginx access logs) but not at the application level with user identity correlation.
- **No configuration change log** — `tutor config save` changes are implicit in Git history, not in a runtime-accessible log.

## 8. Lightweight Implementation Plan (Aspirational, P3)

This section is a starting point, not a commitment. The intent is to close the highest-value gaps with minimal engineering effort.

### Phase 1 — Low-effort, high-value (no new infrastructure)

| Action | Effort | Value |
|--------|--------|-------|
| Ship `tracking.log` to Loki via Promtail | Low — add a Promtail scrape config | Closes pod-restart data loss gap |
| Add Loki alert rule for bulk admin deletions in `django_admin_log` | Low — Prometheus alerting rule | Early warning on accidental/malicious admin actions |
| Document `VideoAccessLog` retention in central DATA_RETENTION_POLICY | Trivial | Closes policy gap |
| Add Grafana dashboard for Purchase Gateway `order_audit_log` query | Medium — read from PostgreSQL via Grafana plugin | Operational visibility |

### Phase 2 — Medium-effort (when Aspects is deployed, T148)

| Action | Effort | Value |
|--------|--------|-------|
| Verify Aspects xAPI event coverage against tracking.log events | Medium | Confirms Aspects replaces or supplements tracking.log |
| Set ClickHouse TTL for `tracking.pii_events` as per DATA_RETENTION_POLICY | Low once Aspects is live | Closes ClickHouse retention gap |

### Phase 3 — Higher-effort (true SIEM, if ever needed)

| Action | Effort | Notes |
|--------|--------|-------|
| Forward Loki logs to an external SIEM (Elastic, Splunk, etc.) | High | Requires SIEM procurement; no current budget |
| Tamper-evident audit log (append-only storage) | High | Likely overkill for current scale and threat model |
| Unified audit schema across all subsystems | High | Significant coordination across Open edX, Purchase Gateway, custom apps |

### Decision criteria for Phase 3

Phase 3 should only be pursued if:
- A compliance audit (ISO 27001, SOC 2, etc.) requires it, OR
- A security incident demonstrates the need for tamper-evident logs

For the current scale and regulatory environment (PDPA Malaysia + GDPR), Phases 1 and 2 are sufficient.
